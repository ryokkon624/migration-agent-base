Sprint 3 Review

#19 — パスワードをハッシュ＋ソルトで保存・照合する

Sprint 3 #19 feature security jpetstore-backend / jpetstore-database

なぜこの改修が必要だったか

問題（S7 是正）

legacy-jpetstore の認証は where account.userid=#username# and signon.password=#password# という平文パスワードの直接比較だった。DB が漏えいすると全ユーザーのパスワードがそのまま漏れる。新スキーマでは m_signon.password_hash varchar(255)（#22 で確保済み）にハッシュを格納する土台はあったが、実際にハッシュ化・照合する仕組み（PasswordEncoder）と、ログイン実証用の「既知PW＋実bcryptハッシュ」のデモユーザーがまだ無かった。

改修前
as-is: signon.password 平文保存・平文比較
m_signon.password_hash 列は存在するが埋める仕組みが無い
ログイン実証用のデモユーザーが無い（弱資格情報は入れられない）
→
改修後
PasswordEncoderConfig（DelegatingPasswordEncoder・既定bcrypt）を Bean 化
{bcrypt}$2a$10$... 形式でハッシュ＋ソルト保存・照合
demo_user（実bcryptハッシュ・弱資格情報なし）をデモシードに追加

AC別 実装内容

✓
AC1 (SBD-5)
パスワードは bcrypt/argon2 等でハッシュ＋ソルト保存・比較（平文保存/平文比較しない）

Spring Security 標準の PasswordEncoderFactories.createDelegatingPasswordEncoder() を採用。既定アルゴリズムは bcrypt（ソルトは bcrypt 内部に自動生成・格納される）で、{bcrypt} プレフィックス付きでエンコードする。将来アルゴリズムを移行する場合も、プレフィックスから判定して既存ハッシュを壊さず段階移行できる Spring Security 公式の推奨方式。

実装メモ（仕様外の判断・変更・妥協点）

PasswordEncoder方式の選定: 素の BCryptPasswordEncoder ではなく DelegatingPasswordEncoder（Spring Security標準・{bcrypt}プレフィックス付き）を採用。理由は「AC別 実装内容 AC1」参照。
実bcryptハッシュの生成手順: デモシードの password_hash は捏造した文字列ではなく、実装した PasswordEncoderConfig.passwordEncoder().encode("Sprint3-DemoLogin!26") を一時テストで実際に実行して得た値をそのまま R__test_user.sql に貼り付けている。

動作確認ポイント（ユーザー確認用）

  • 1
    DB内のdemo_userのpassword_hashがbcrypt形式であること SELECT password_hash FROM m_signon s JOIN m_account a ON a.user_id=s.user_id WHERE a.username='demo_user'; の結果が {bcrypt}$2a$... で始まり、平文 Sprint3-DemoLogin!26 のままではないこと
  • 2
    j2ee/j2ee ではログインできないこと curl で POST /api/auth/login に {"username":"j2ee","password":"j2ee"} を送ると401が返ること（j2eeユーザーはシードに存在しない）
  • 3
    demo_user / Sprint3-DemoLogin!26 で正しくログインできること 実機確認手順は #18 レビューHTMLの「動作確認ポイント」参照（login→保護resource→logoutの一連疎通）
