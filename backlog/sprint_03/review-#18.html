Sprint 3 Review

#18 — サインオン/サインオフ（セッション再生成・元URL復帰）を提供する

Sprint 3 #18 feature jpetstore-backend backend REST + Security のみ
今スプリントのスコープ（重要）

本 Issue は backend（REST API + Spring Security）のみ実装しました。Vue3 SPA のログイン画面・Pinia authストア・ルーターガードでの元URL復帰UXはフロント責務のため今スプリント対象外です。

  • backend で充足済み：login/logout/refresh REST・UserDetailsServiceのDB結線・CSRF・セッション固定化対策・弱資格情報の排除
  • #24（E6 フロント土台・Sprint 5予定）へ持ち越し：Vue ログイン画面、login/logout/refresh呼び出し＋CSRF cookie→header、元URL復帰UX（AC7/AC8として反映済み）

なぜこの改修が必要だったか

問題

#23（Sprint 2）で JWT httpOnly Cookie・CSRF・認可の「土台」は整備済みだったが、AuthController には POST /api/auth/refresh しか無く、credential（username/password）を交換して最初にログインする入口が存在しなかった。また UserDetailsService がDBに結線されておらず、Spring Securityの標準的な認証フロー（AuthenticationManager）も未配線だった。

改修前（#23時点）
AuthController: refreshのみ（login/logout無し）
UserDetailsServiceがDBに未結線
AuthenticationManager未定義
→
改修後
POST /api/auth/login・/logout を追加
JdbcUserDetailsServiceがm_account×m_signonを参照
AuthenticationManager(DaoAuthenticationProvider)を結線
ログイン成功=新規access/refresh発行(固定化対策)

実装メモ（仕様外の判断・変更・妥協点）

syncTestSeedタスクの新設を見送り: 計画時は「新規gradle syncTestSeedタスク」を想定していたが、jpetstore-backend/src/test/resources/flyway/sql/README.mdに「flyway/sql-testはbackendの統合テストへ同期しない・各テストが自己完結でフィクスチャをINSERTする」という既存方針が確立済みだったため、それに合わせた。#19のデモシード検証はjpetstore-database側のTestcontainersテストに、#18のlogin/logoutテストはbackend側で自己完結のフィクスチャINSERTにした。
HttpRequestMethodNotSupportedExceptionのバグ修正: AC-neg2の自動テスト作成中に、GET等の未マッピングメソッドが500に丸められる既存バグ（#23由来）を発見し、本Issueのスコープで修正した（詳細は「AC-neg2」参照）。
申し送り: CSRFトークンのconsume-then-regenerate挙動（#24フロント実装時に要考慮）
手動動作確認で、CSRF（XSRF-TOKEN）Cookieが状態変更（非GET）リクエスト成功のたびにサーバー側で失効し、次のGETリクエストで新しいトークンが再発行される挙動を発見した。/api/auth/refresh（#23由来の既存エンドポイント）でも同一現象を確認済みのため、#18/#19で新規に混入したものではない。SPA実装（#24）側は、連続してPOST/PUT/DELETEする場合に毎回最新のXSRF-TOKENCookie値をヘッダへ載せる、または各POST前にGETでトークンを再取得する設計が必要。
