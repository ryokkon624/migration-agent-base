実装メモ（仕様外の判断・変更・妥協点）

  • Spring Boot 4.1の自動構成ObjectMapperはJackson 3系（tools.jackson.*） — com.fasterxml.jackson.databind.ObjectMapper（Jackson 2系）はSpring Bean未登録。Jackson 2系はjjwt-jackson/springdoc等サードパーティ内部利用のみ。後続ドメインStoryがJSON処理する際に踏襲すべき知見。
  • Spring Boot 4.1 / Spring Security 7でのパッケージ移動 — DataSourceAutoConfiguration→org.springframework.boot.jdbc.autoconfigure、UsernamePasswordAuthenticationFilter→org.springframework.security.web.authentication、@AutoConfigureMockMvc→org.springframework.boot.webmvc.test.autoconfigure（spring-boot-webmvc-testアーティファクトを明示追加）。実機ビルドで判明。
  • 統合テスト基盤を新規構築 — support.IntegrationTestBase（Testcontainers MySQL 8.4 + Flyway自動適用）。適用スキーマはjpetstore-databaseのflyway/sqlをsrc/test/resources/flyway/sqlにコピー（filesystem参照ではなく単体clone可能にするため）。./gradlew syncTestSchemaタスクで同期。
  • 保護テストエンドポイント1本の使い回し — GET /api/secured/ping（@PreAuthorize("hasRole('ADMIN')")）1本のみを追加し、simulateErrorパラメータでAC4（例外正規化）・AC8（409マッピング）も同じエンドポイント経由でend-to-end実証。「保護テストエンドポイント1本のみ」というスコープ制約を守りつつ複数ACをカバーした。

動作確認ポイント（ユーザー確認用）

  • 1
    DB資格情報・JWT鍵を設定しないと起動しないこと DB_USERNAME/DB_PASSWORD/JWT_SECRETを未設定のまま ./gradlew bootRun すると、起動時に明確なエラーで失敗する（.env.exampleをコピーして値を設定すれば起動できる）
  • 2
    認証なしで保護APIにアクセスすると401、権限不足だと403になること Cookie無しで GET /api/secured/ping を叩くと401、USER権限のトークンだと403、ADMIN権限のトークンだと200が返る（いずれもJSONでcodeフィールドを含む正規化レスポンス）
  • 3
    CSRFトークンなしでの状態変更リクエストが拒否されること CSRFトークンなしで POST /api/auth/refresh を叩くと403で拒否される
  • 4
    refresh tokenだけでaccess tokenを再発行できること（credential不要） 有効なrefresh CookieでCSRFトークン付きの POST /api/auth/refresh を叩くと204が返り、新しいACCESS_TOKEN Cookieが発行される
  • 5
    エラー時にスタックトレースや内部情報が漏れないこと 存在しないリソース・競合・想定外エラーいずれも「code / message / path / timestamp」のみのJSONが返り、Javaのクラス名やファイルパスが含まれない
  • 6
    認可に失敗したアクセスが監査ログに記録されること t_audit_logテーブルにevent_type=AUTHZ_FAILURE・result=DENIEDで1行記録される（誰が・いつ・どのアクションで拒否されたか追跡可能）
