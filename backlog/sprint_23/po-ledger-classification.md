- **この文書がやらないこと**: **実測（どのテストが観測点になっているかの名指し）は DEV 分担**。ここでの `観測可能` は「観測点がある」という意味ではなく「**比較が成立する**」という意味。`観測可能` × DEV の実測結果を突き合わせて、SM が最終的に「観測点あり」か「穴」かを決める。

## 判定の3値（#52 AC2 のうち PO が決める部分）

| 値 | 意味 |
| --- | --- |
| **観測不要** | もはや差分でない。旧に対する差分として宣言されたが、その後の実装完了・スコープ決定によって**比較する意味が消えた**。 |
| **構造的に観測不能** | **比較対象そのものが存在しない**。旧側に対応概念が無い／突き合わせる単位が定義できない。 |
| **観測可能** | 上2つに当たらない。旧新で比較しうる振る舞いの差分として**今も生きている**。 |

**運用方針**: 「観測不要」「構造的に観測不能」は判定を楽にするための逃げ道ではない。Phase 4 の価値は「正しく再現したと言える範囲を、**言えない範囲と一緒に**明示すること」なので、**迷ったら `観測可能` に倒す**（＝穴になりうる側へ倒す）。

## C. SM 依頼の「PO 判断待ち」事項への判断

### C-1. L3 §3-5「在庫枯渇（denial-of-inventory）」— **台帳追記は不要。ただし受容の記録先は ID-8 ではない**

**PO 判断（3点）**:

1. **台帳へ新規 ID を追加しない**。台帳は「**旧と違ってよい／違うべき**」を宣言する場であって、絶対的なセキュリティ特性を書く場ではない。旧のカード必須検証は `OrderValidator#validateCreditCard` の `rejectIfEmpty` 3本（メッセージが文字どおり `"FAKE (!) credit card number required."`）で、**任意の1文字を入れれば通る**。旧に決済ゲートは存在せず、認証済みユーザーが在庫を減らし放題である点は**旧新で変わらない**（＝差分ではない）。
2. **「ID-8 の帰結」として ID-8 に受容明記するのも不正確**。上記のとおり ID-8（カード列・必須検証の撤去）は「在庫を枯渇させられる」能力を**新たに作っていない**。撤去されたのはダミー欄の非空チェックだけで、攻撃コストは1文字ぶんしか変わらない。ID-8 の行にこの帰結を書くと、**差分でないものを差分の帰結として記録する**ことになる。
3. **記録するなら ID-1 側が正確**。「在庫が 0 になると他の顧客が買えなくなる」という**影響の質**は、**在庫ガードを入れた ID-1 の帰結**である。旧はガードが無いので在庫がマイナスでも注文が通り続け、枯渇が他の顧客をブロックしない。つまり「枯渇が意味を持つようになった」のは ID-1 の副作用で、これは**受容済みトレードオフとして ID-1 に1行足す**のが筋（ID-11 が「レート制限はログイン/登録に適用」と宣言済みで、**状態変更 API を対象外にしている**ことと合わせて読めるようにしておくと尚よい）。ただし **AC6「並べ替えのみ」・AC-neg3「憶測で ID を足さない」に従い、本 Story では台帳を書き換えていない**。追記の可否は SM からユーザー判断を仰いでほしい。

**処理（2026-08-21 ユーザー判断）**: 上記どおり**台帳に新規行は作らず**、**ID-1 の行内に「受容済みの帰結」として1行追記済み**（在庫ガード導入の副作用であること／ID-8 の帰結ではない根拠／現時点で受容／本番基盤の整備決定時に #45・#43・#46 と束ねて再評価、を含む）。<br>なお SM の verification で**さらに強い裏付け**が出た: 旧の `OrderValidator` は **Struts 経路からは呼ばれない**（`NewOrderAction` は検証を挟まず `insertOrder` を直呼び。`OrderValidator` を参照するのは Spring MVC 経路の `web/spring/OrderFormController.java:87` のみ）。つまり稼働 legacy では**1文字の非空チェックすら走っていない**。結論は実行経路まで含めて成立する。

**リスクとしての受容可否（PO の結論）**: **現時点では受容する**。理由は (i) 旧に対する退行ではない（旧は無制限にマイナス在庫まで枯渇させられた）、(ii) 攻撃には認証済みアカウントが必要、(iii) 決済が無いため金銭的損失は発生せず、被害は在庫数値の消費に限られ復旧可能、(iv) 状態変更 API のレート制限は現行スコープ外（ID-11 が適用範囲をログイン/登録と宣言済み）。**ただし本番デプロイ基盤/本番プロファイルの整備を決めた時点で再評価する**（#45・#43(B)(E)・#46 の再判定と同じタイミングに束ねる。`memory/po/short_term.md` の運用に合わせる）。状態変更 API のレート制限は、その時点で将来 Story の候補として扱う。
