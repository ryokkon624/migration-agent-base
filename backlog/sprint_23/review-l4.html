03この報告書が主張しないこと

4 本のゲートが PASS したことは、「何も変わっていない」ことを意味しない。

  1. 台帳の網羅性は保証されていない。 台帳が 31 → 33 件になったのは L4 が 2 件見つけたからであって、全数走査をした訳ではない。3 件目が無いとは言えない。
  2. 「観測点あり」31 件のうち 6 件は部分観測。 宣言の全体を見ているわけではない。
  3. 穴が 2 件残っている（ID-30・ID-33）。 今スプリントでは埋めていない。起票しただけである。
  4. 旧新の直接比較が成立しているのは 33 件中 4 件。 「旧と同じ結果になる」を旧の実測値と突き合わせて示せている範囲は狭い。
  5. L2 が踏んでいる legacy の分岐 28/34 は「理論上限」ではない。 SqlMapItemDao の 3 分岐はシナリオを足せば踏める。正しくは「現行シナリオ集合のスコープ内での上限」。
  6. 比較モデルが最初から外しているフィールドがある。 カード列（ID-8）・courier/locale（ID-21）・orderstatus/linenum（ID-22）・採番 ID（ID-23）・password（ID-2）・mylist/banner（ID-7）・配色（ID-31）。除外は「そこに差分がある」という宣言であって、差分の観測ではない。
  7. L3 の PASS は before の findings に対するもの。 after 側には Low 4 件が残っており（#42–#47 で起票済み）、当該レポート自身が「完全な clean とは書けない」と書いている。
  8. L1 の 951 テストは AC 準拠を見ている。 「仕様どおりに動く」と「旧と同じに動く」は別である。
  9. 注文の二重送信は未決着。 旧新差分でない公算が高いという判定に基づく保留であり、実測していない。「起きない」証拠も「起きる」反証もテスト資産に存在しない。
  10. これは検証結果の突き合わせであって、受入テストではない。 ライブ PoC 以外に、旧新を同時に動かして人が比べた記録は含まれない。

04L4 が台帳自体に見つけたもの

L4 は「台帳どおりか」を確認する工程だが、その過程で台帳そのものの誤りが見つかった。 台帳が判定の分母である以上、これは L4 の一次成果である。

ID-27 訂正 as-is「日英 JSP 同梱」は誤り。legacy に日本語資産は 1 つも存在しない。langpref は保存されるだけで描画に一切影響しない。
ID-28 訂正 as-is「在庫状況表示なし」は誤り。旧は生の在庫数をそのまま画面に出していた（Item.jsp:37-43）。差分は「表示の有無」ではなく「生の在庫数の露出 → status のみ」——as-is が誤っていると、差分の性格そのものを読み違える。
ID-10 訂正 after「セッション再生成」は新の構成と字義上かみ合わない。新は STATELESS でセッション自体を作らない。趣旨（固定化が成立しない）は不変だが、字義どおりに観測点を作ると空振りする。
ID-32 追記 未台帳の差分。認証状態の保持方式（HTTP セッション → 完全ステートレス）。セッションに同居していた個別状態は各々宣言されていたが、方式そのものが宣言されていなかった。
ID-33 追記 未台帳の差分。カート一覧のページング廃止（旧 4 件/頁 → 全件表示）。ID-20 が「カタログ一覧」限定だったため、カート側がどの ID の担当でもなくなっていた。
18 → 17 引用元レポートの「全 18 シナリオ」は 17 が正（off-by-one）。一次データ 3 系統がすべて 17。ゲート値は機構出力なので影響なし。
SM の誤り 「台帳 ID-26 の CVE 根拠が L3 と食い違う」という SM の指摘は取り下げ。台帳＝jpetstore-database の 8.0.33、L3＝jpetstore-backend の 9.5.0 で対象アーティファクトが別だった。座標まで一次データで確認してから「食い違い」と呼ぶこと。

ID-33 が穴なのは偶然ではない。 ID-33 は L4 が今回はじめて台帳に載せた差分である。台帳に載っていなかったものに観測点が作られているはずがない—— 「台帳に載せる」と「観測点を作る」が同じ駆動から出ている以上、これは自然な因果である。 逆に言えば、台帳の抜けは観測点の抜けとして必ず現れる。

05次の一手を、台帳から導いた

L2 のカバレッジ軸は枯れていた（28/34）。そこで「カバレッジが低いから足す」ではなく 「台帳 ID に観測点が無いから足す」へ駆動を入れ替えた。その結果——

L2 のカバレッジの穴と、L4 の観測点の穴が同一だった。

item-detail-missing（不存在 itemId で viewItem.do）を 1 本足すと、 ID-14 の 2 本目の観測点になり（台帳が挙げる 3 経路のうち、L2 で見ているのは今 1 本だけ）、 同時に SqlMapItemDao.getItem の未踏分岐をちょうど踏む。

駆動を入れ替えても、カバレッジ面で失うものが無い。これが「観測点の質へ軸を移す」という提起に対する、実測での回答である。

#54 観測点の穴を埋める — ID-30（下書きがリロードで消えること）・ID-33（カートが全件表示であること）。どちらも「無いこと」を固定する assert が存在しない。
#55 部分観測の補強と退行検知器の追加 — item-detail-missing・item-out-of-stock-add・STATELESS の assert（現状 0 件＝設定を戻しても赤くならない）・t_order.order_id の AUTO_INCREMENT assert。

いずれも今スプリントでは実装していない。起票までがスコープとした。 #55 はカバレッジ数値を達成判定に使わないことを否定 AC に明記している——駆動を戻さないため。
