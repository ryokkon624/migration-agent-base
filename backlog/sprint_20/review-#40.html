Sprint 20 Review · Security Bug Fix

#40 — 注文確定の失敗が監査に残らず500になる
（入力制約欠落・ID-22未達）

Sprint 20 #40 bug security Medium (L3 N3 + N11)

発生事象（SEC/スキャナ実測）

OrderApplicationService.placeOrder の catch は InsufficientStockException のみを捕捉していた。それ以外の失敗（DB例外等）は ORDER_CREATE の監査行が一切残らない。 さらに OrderAddressRequest には @Size が皆無で、PlaceOrderRequest.shipping にも @Valid が付いていなかったため、長すぎる住所や欠落したshipping項目がDB制約違反として500に落ち、監査ゼロのまま消えていた。 これは意図差分台帳 ID-22（「注文作成は成功・失敗いずれもORDER_CREATEとして記録」）に正面から反する。

修正前（バグあり）
$ POST /api/orders (postalCode: 40文字) ← 500 Internal Server Error t_audit_log: 監査行ゼロ（ORDER_CREATE記録なし）   $ POST /api/orders (useSeparateShipping=true, shipping項目が空) ← 500 Internal Server Error @Validがカスケードされずship_address1等のNOT NULL列違反
成功時は正しく記録されることは対照確認済み（在庫不足の失敗監査は既存機能でOK）
修正後（正常）
$ POST /api/orders (postalCode: 40文字) ← 400 Bad Request 入口検証で弾かれる（Bean Validation）   $ POST /api/orders (useSeparateShipping=true, shipping項目が空) ← 400 Bad Request shippingにも@NotBlank/@Sizeがカスケード   $ POST /api/orders (在庫不足以外の想定外の失敗) ← 500のまま(想定外は500)だがt_audit_logに1行残る ORDER_CREATE/FAILUREが必ず記録される
新設 OrderFailureAuditL3RegressionSpec（IT）で固定

原因分析

🔍 失敗監査の対象が狭すぎる ＋ 入力検証が同一backend内で非対称
DTO@Size付与状況（修正前）
AccountController.java（アカウント編集）全項目に付与済み
OrderController.java（注文住所）皆無

同一backend内で対称であるべき検証パターンが非対称だった。加えて、Bean Validationはネストしたrecordへ @Valid 無しではカスケードしないため、shipping の各項目は @NotBlank すら適用されていなかった （SECの想定に無く、Refinementで新規発見）。DataIntegrityViolationException専用ハンドラが不在で、これらの入口をすり抜けたDB制約違反は catch-allが500に丸めていた。

実装メモ（仕様外の判断・変更・妥協点）

OrderFailureAuditL3RegressionSpecの失敗注入方式

AC2/AC3導入後、入力検証由来の500経路はBean Validationで400に塞がれるため、「在庫不足以外の想定外の失敗」を実HTTP経由で再現するには 疑似的なDB層失敗の注入が必要だった。MockitoSpyBeanでOrderRepository#insertHeaderを1回だけ失敗させる方式を採用した （在庫減算〔後続処理〕が発生しない実装順序を確認済み）。

意図的な設計: address2の列幅は80（AccountEditRequestの40とは非対称で正しい）

OrderAddressRequest.address2の80はt_order由来。AccountEditRequest.address2の40は m_account由来であり、別テーブル由来の正しい非対称（reviewer churn防止のため明示）。

意図的な設計: DataIntegrityViolationExceptionハンドラは防御多層

AC2/AC3の入口検証（@Size/@Valid）が機能する限り、このハンドラの経路（AC-neg1）からは通常到達しない。それでも新設したのは、 入口検証をすり抜けた想定外のDB制約違反に対する多層防御のため。GlobalExceptionHandlerSpecの単体テストで独立に固定した （AC-neg1のIT経路では検証不能なため）。
