#39 — 過大長URIで認可失敗の監査記録が消え、
403が401に化ける（監査抑止）

Sprint 20 #39 bug security Medium (L3 N2 + N14) cross-repo: backend + database

発生事象（SEC ライブPoC実測）

AuditLogRecorder が 認可失敗のURIを長さ検証なしで t_audit_log.action VARCHAR(100) へINSERTしていた。 URIが101文字以上だと Data too long でINSERTが例外→セキュリティハンドラ内から例外送出→/errorへの ERRORディスパッチ（JWTフィルタ非適用）に落ちる。結果、403が401に化け、「誰が・何をしたか」の監査行が消える。 認証済み攻撃者はURIを伸ばすだけで自分の認可失敗の痕跡を任意に消せた。

修正前（バグあり）
$ curl (demo_userで) /api/orders/909090909 (21字) ← 403 Forbidden 監査: actor=demo_user, action=/api/orders/909090909, DENIED（正常）   $ curl (demo_userで) /api/orders/<81個の0>909090909 (102字) ← 401 Unauthorized 監査: actor=NULL, action=/error, DENIED（誰が/何をが両方消失）
境界は列幅(100)と厳密一致。orderIdはLongなので先頭ゼロ埋めでURI長を自由に伸ばせる。未認証でも成立
修正後（正常）
$ curl (認証済みで) 200文字級URIの他人注文を参照 ← 403 Forbidden（維持） 監査: actor=demo_user, action=<先頭100文字>, DENIED（残る）   $ 未認証リクエストを quota上限超えて連続送出 ← t_audit_log行数が上限で頭打ち 抑止事実は suppressed_count + WARNログに残る（黙って消えない）
新設 AuditSuppressionL3RegressionSpec（IT）で固定

実装メモ（仕様外の判断・変更・妥協点）

既存ITの偽陰性化回避

AC3導入により未認証recordAuthzFailureにquotaゲートが掛かるため、IT間で共有される単一MySQLコンテナ上でカウンタが積み上がると、 未認証401の監査行をアサートする既存specが偽陰性化しうる。AuditLogRecorderSpec・OwnershipAuthorizationEndToEndSpec・ SecurityEndToEndSpecのsetup()にDELETE FROM t_audit_write_quotaを追加して対処した。

マイグレーション数アサーションの更新

V00_000_014追加に伴い、既存のflyway_schema_history件数アサーション（13→14）をIntegrationTestBaseSmokeSpecで更新した（新規マイグレーション追加時の定型対応）。

意図的な設計: quotaは未認証（actor==null）限定

認証済みの403にはquotaを掛けない。掛けてしまうと、攻撃者が自分の枠を意図的に使い切ることで以降の自身の認可失敗を無記録化でき、 本Issueが直している監査抑止（N2）をそのまま再導入してしまうため。この理由はAuditWriteQuotaServiceのjavadocに明記し、将来の安易な一般化を防いでいる。

意図的な設計: truncateの4列拡張（AC1の要求は action のみ）

target_type/target_id/actor_usernameの3列も同じ経路でINSERT失敗しうるため、防御多層化として一緒にtruncate対象へ含めた。

!
SM verification（コア精読）で1件の確定所見を検出

AuditLogRecorder.recordAuthzFailureのauditWriteQuotaService.tryAcquire呼び出しが、実装当初は例外保護の外にあった。 tryAcquireは@Transactional(REQUIRES_NEW)で新規コネクション取得を伴うため、未認証フラッド時（＝まさにquotaが守ろうとしている状況）に コネクションプール枯渇等で例外を投げやすい。これが呼び出し元4経路へ素通りすると、#39が修正対象にしているN2と同一の失敗モード（403/401が化け・監査も残らない）を、 トリガを「過大長URI」から「quotaのDBエラー」に変えただけで再現してしまう状態だった。TDDの否定ACテストが「mapper.insertの失敗」しか固定しておらず、 実装時のRED→GREENサイクルでは検出できなかった。

🔧
是正: isWithinQuotaヘルパーへ切り出しfail-open化

tryAcquire呼び出しをtry/catchで保護。例外時はfail-open（枠ありとみなして監査INSERTへ進む・ERRORログは残す）とした。 fail-closed（例外時にreturn）はquota障害自体が新しい監査抑止経路になるため不採用と判断し、javadocに明記した。

✓
デルタ再レビュー: 3観点クリーン

是正差分に対する3観点の再レビューは指摘なし。AuditLogRecorderBestEffortSpecに3件のテスト（fail-open伝播なし・insertへ進むこと・ERRORログ）、 AuditSuppressionL3RegressionSpecに1件（未認証401のe2eでquota例外時も本来のErrorResponseが返ること）を追加して固定した。
