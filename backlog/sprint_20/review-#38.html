#38 — JWT署名鍵が公開のplaceholder値で稼働し、
資格情報なしで任意ユーザ/ADMINのトークンを偽造できる

Sprint 20 #38 bug security Critical (L3 as-run)

発生事象（SEC ライブPoC実測）

backend は git 追跡下の .env.example に平文で書かれた placeholder 鍵（please-replace-with-a-random-secret-of-at-least-32-bytes）で JWT を署名・検証していた。起動時の fail-fast 検証は鍵の長さ（32byte以上）しか見ておらず、この既知の公開値でも普通に起動してしまう。 その結果、リポジトリを読めるだけの第三者が、資格情報なしに任意ユーザ・任意ロール（ADMIN）の有効な JWT を偽造できる状態だった。

原因分析

🔍 fail-fast検証が「鍵の長さ」しか見ていなかった

JwtProperties.java:19,30-37（修正前）は最小鍵長（32byte）のみを検証していた。 .env.example の placeholder は56byteあり、この検証を素通りする。README の手順も 「.env.example を .env にコピーして値を設定する」という導線で、値の差し替えを強制していなかった。 対照として、別の秘密鍵で署名したトークンは正しく401になることをSECが確認済み＝署名検証ロジック自体は正常。根本原因は「鍵そのものが公開されていること」。

検証項目 修正前 修正後
鍵の長さ（≥32byte） 検証あり 維持（既存のまま）
既知 placeholder / 弱いリテラル 検証なし denylist で拒否（AC1）
最小エントロピー（ユニーク文字数） 検証なし 24未満は拒否（AC2・補助）

⚠️ 破壊的変更（Sprint Reviewでの実機確認に影響）

⚠️
.env.example をそのままコピーした .env では backend が起動しなくなります

今回のdenylistには .env.example の実リテラル値が恒久的に含まれるため、README の手順どおりコピーしただけの .env（値を差し替えていないもの）は起動時に必ず拒否されるようになりました。既に稼働・開発中の環境で JWT_SECRET が please-replace-with-a-random-secret-of-at-least-32-bytes のままの場合は、 openssl rand -base64 32 等で生成した値へ差し替える必要があります。

✓ DEVがローカル環境の .env を調査した結果、JWT_SECRET は既に64文字・ユニーク43種の乱数値へローテート済み （L3 PoC実施後にSECが差し替え）でした。denylist・エントロピー検証とも問題なく通過するため、現ローカル環境では追加作業は不要です。

実装メモ（仕様外の判断・変更・妥協点）

既存テスト鍵フィクスチャの一括是正（不可避な付随作業）

AC2（ユニーク文字数24未満で起動不可）を導入すると、既存の統合テストが使っていたテスト用鍵（例: "a" * 32＝ユニーク1種）が軒並みコンテキスト起動失敗になることが計画時点で判明していた。 新設 support/TestJwtSecrets（STRONG/ENV_EXAMPLE_PLACEHOLDER/LOW_ENTROPY）に集約し、 5ファイル（IntegrationTestBase/JwtServiceSpec/JwtAuthenticationFilterSpec/JwtPropertiesSpec/ApplicationBootFailFastSpec）を一括是正した。

ApplicationContextRunner の Duration 変換の罠

起動失敗そのものを固定する新規 JwtSecretContextFailFastSpec を素の ApplicationContextRunner で組んだところ、 Spring Boot 拡張の Duration コンバータが無いため JWT_SECRET の値に関わらず常にコンテキスト起動が失敗し、 AC-neg1/AC-neg2 が「別の理由での起動失敗」に紛れて偽陽性GREENになる罠があった。conversionService という bean 名で ApplicationConversionService を明示登録して解消した。

宙吊り参照の是正

JwtPropertiesSpec javadoc の {@link SecretFailFastSpec}（実在しないクラス）を、実在する {@link ApplicationBootFailFastSpec} へ修正した（#38 改修方針4のとおり）。

意図的な設計: .env.example の値そのものは変更しない

PO判断により、.env.example の JWT_SECRET 値は据え置いた。値を変えずdenylistへ恒久収録することで 「コピーしただけでは起動しない」＝実運用不能化を達成する。将来 .env.example の値を変更しても、過去に配布した値を denylist から削除しないこと（既存の .env コピーが黙って残り続けるため）。DBの資格情報（DB_USERNAME/DB_PASSWORD）は 本Issue対象外（別Issue #43(C)(E) のスコープ）。
