Sprint 17 Review

#15 — パスワード変更に現在パスワード確認（再認証）を必須にする

Sprint 17 #15 security / E4 2-repo（backend + frontend）

なぜこの改修が必要だったか

問題

これまでSPA上にはパスワードを変更する画面/APIが一切存在しなかった。もしセッションが乗っ取られた場合（Cookie窃取等）、現在パスワードの確認なしにパスワードを変更できる経路があると、正規ユーザーがアカウントを取り戻せなくなる（S6是正）。パスワード変更は「現在パスワードによる再認証」を必須にし、変更成功時はセッションを新しいトークンにローテートする必要がある。

改修前
パスワード変更の画面/APIが存在しない
userId起点で現在パスワードハッシュを取得する経路がない（既存はusername起点・login専用）
アカウント編集画面からパスワード変更への導線がない
→
改修後
/account/password（PasswordChangeView.vue・requiresAuth）
POST /api/account/password → 現在PW再認証 → 強度検証 → bcrypt更新
現在PW誤り=422／弱PW=400／未認証=401／CSRF欠落=403 の三系統分離
成功時は issueTokensFor で現在セッションのトークンをローテート（Q3）

実装メモ（仕様外の判断・変更・妥協点）

  • HttpStatus.UNPROCESSABLE_ENTITY は Spring Framework 7.0 で非推奨化されていた: UNPROCESSABLE_CONTENT（値=422は不変・RFC 9110の呼称変更）へ是正した。JSON応答の code フィールドは既存の "UNPROCESSABLE_ENTITY" 文字列のまま維持している。
  • PasswordChangeControllerSpec の m_signon フィクスチャは自己INSERT: AuthLoginLogoutSpec と同型で、テスト自身が passwordEncoder.encode() で生成した既知パスワードのbcryptハッシュを用意した。
  • SignonCustomMapper.updatePassword はPOJO（SignonUpdateCustomEntity）を単一パラメータとするアノテーション方式: 複数 @Param スカラーではなくPOJOにした理由は、AuditProgramInterceptorが警告する「paramがMapの場合の意図しないput混入」を構造的に回避するため（既存 AccountUpdateCustomEntity と同じ設計判断）。
  • 実機 bootRun 起動確認は省略した: SecurityConfig は無変更（新規permitAll追加なし）であり、新規エンドポイントは統合テスト（実際のSecurityフィルタチェーンを全経路通過）で401/403/404/405/422/400/204の全応答を実証済みのため、十分にカバーできていると判断した。

動作確認ポイント（ユーザー確認用）

  • 1
    アカウント編集画面（/account/edit）から「Change Password」ボタンでパスワード変更画面に遷移できること これまで遷移先が存在しなかった
  • 2
    現在のパスワードを間違えて入力すると変更が拒否され、明確なエラーメッセージが表示されること 「Current password is incorrect.」等。パスワードは実際には変更されない
  • 3
    正しい現在パスワードと強いパスワードを入力すると、変更が成功し成功メッセージが表示されること 「Your password has been changed.」
  • 4
    パスワード変更後、再ログインを求められることなくそのまま画面操作を続けられること 現在セッションのトークンが裏でローテートされているため（成功画面から他画面へ遷移して確認）
  • 5
    弱いパスワード（英小文字のみ等・1種類の文字種のみ）を入力すると、送信前にエラー表示されること フォーム送信を待たずにその場でフィードバックされる
