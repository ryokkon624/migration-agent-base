Sprint 12 Review

#29 — Cart を参照実装に Repository 層導入＋集約化
（Application Service の Mapper 直呼び解消・PoC）

Sprint 12 #29 refactor jpetstore-backend PR #11

なぜこの改修が必要だったか

問題

CartApplicationService（Application層）が MyBatis の CartCustomMapper を直接注入し、*CustomEntity（Infrastructure層）を直接 import・使用していた。これは backend-conventions §1（Entity は Infrastructure 層に閉じる・依存性逆転）に違反したドリフトで、コードベースには Repository interface が1つも存在しなかった（本Issueが初回）。在庫上限・Math.addExact オーバーフロー検出・merge クランプ等の不変条件も、集約ドメインモデルではなく Service 内に手続き的に実装されていた。

改修前
CartApplicationService → CartCustomMapper（直接注入）
*CustomEntity（infra）を Application 層で直接扱う
不変条件（在庫上限・overflow・クランプ）は Service 内の手続き的コード
Cart/CartItem は anemic record（ロジックを持たない）
→
改修後
CartApplicationService → CartRepository（domain interface）
MyBatisCartRepository（infra実装）が Mapper/Entity を隠蔽
不変条件は Cart/CartItem のコマンドメソッドへ移設
Cart/CartItem は集約（private ctor＋reconstruct()）
ℹ️ 本コードベース初の Repository / Converter / reconstruct() 実装。#30（Catalog/Account/Order への全体展開）が本実装をテンプレートとして踏襲する。API・エンドポイント・レスポンス形状・挙動は完全に不変（内部リファクタのみ）。

設計の核心（#30 が踏襲する先例テンプレ・ユーザー承認済）

D1＝案A

単一の rich な Cart/CartItem を採用。stockQuantity（在庫qty）は private 内部保持し、外向きは stockStatus()/exceedsStock()/lineTotal()/quantity() の射影アクセサのみ公開。生の stock getter が無いため、在庫数非露出（ID-28）が型レベルで強制される。

D2＝案A

CartRepository は集約全体を差分保存する save(Cart) ではなく、細粒度の upsertItem/removeItem＋findStock（ドメイン語彙・1ユースケース=1行書込）を採用。dirty-tracking や全行upsertが不要で、現行のSQLパターンと同等の書込コストを維持。

D3

在庫コンテキストは findStock(cartId, itemId) で個別解決し、集約へ都度注入する構造にした。#28（merge の N+1 解消）はこのメソッドを findStocks(cartId, List<itemId>) へバッチ拡張するだけで対応できる seam を確保（本Story ではN+1自体は解消しない）。

実装メモ（仕様外の判断・変更・妥協点）

Repository のメソッド面: Issue本文が例示した save(Cart)（集約全体差分反映）ではなく、D2=案A（ユーザー承認済）どおり細粒度の upsertItem/removeItemを採用。dirty-tracking や全行upsertが不要な分、余分な書込・実装コストを避けた。

監査WHOカラムの解決責務: create_user_id/update_user_id の解決を CartApplicationService から MyBatisCartRepository へ移した。永続化アクセスの唯一の入口であるRepositoryがWHO解決も担うことで、Application層は認可の主体と監査の主体が同一ユーザーである事実をRepositoryへ都度渡す必要がなくなった。

Cart.identity(cartId): perf是正で追加した軽量ハンドル。itemsを空のまま保持するため「表示用の完全なCart」とは別物であることをJavadocで明記し、コマンドメソッド呼び出し専用と限定した。

Spockの既知の罠が2回目発生: given:の裸stubとthen:の引数一致インタラクションを同一メソッド呼び出しに分けて書くと、then:側が優先されgiven:側の戻り値が無視される（Sprint11 OrderApplicationServiceSpecで既知の挙動）。perf是正の新規テストで再発しRED化したため、then:ブロックの1つのインタラクションにmatcherと>>をまとめる形に統一して解消した（2回目発生のためRetroでSkill昇格を判定予定）。
