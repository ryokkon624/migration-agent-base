#8 — 注文確定でサーバ再計算・在庫の原子的引当・整合性を保証する

Sprint 11 #8 feature security / E3 cross-repo: backend + frontend

なぜこの改修が必要だったか

問題（legacy JPetStoreの脆弱性）

legacyの注文確定は以下の3点で「クライアントを信頼しすぎる」実装だった。

  • 確定操作が GET newOrder.do?confirmed=true（冪等でない状態変更がGETリンク・CSRFトークンなし）
  • 金額はセッション/フォームの値をそのまま使い、サーバー側での再計算をしていない
  • 在庫はガード無しの単純な減算で、同時に複数人が注文すると在庫がマイナスになりうる（売り越し）
改修前（legacy Struts1）
確定 = GET確定リンク（CSRF無し・冪等でないGET）
金額 = セッション/フォーム値をそのまま信頼
在庫 = ガード無し減算（同時発注で売り越し可能）
採番 = select→+1→update（非アトミック）
注文作成の監査記録なし
→
改修後（本Story）
確定 = 非冪等 POST /api/orders（CSRF必須）
金額 = 確定時点の m_item.list_price でサーバ再計算
在庫 = ガード付きUPDATE（affected rows==0で失敗・行ロックで直列化）
採番 = AUTO_INCREMENT（原子採番）
成功・失敗とも監査ログへ記録（失敗は別トランザクション）
在庫qty=1へ2ユーザーが同時注文（改修前の設計だと）
-1
両方成功し在庫がマイナスになりうる（売り越し）
本Story実装後（実DBで2スレッド同時実行を実証）
0
片方のみ成功・もう片方は409で拒否。在庫は0で停止

AC2
在庫はガード付きアトミック減算で引当（affected rows==0を在庫不足として注文失敗）

実装メモ（仕様外の判断・変更・妥協点）

① OrderControllerのテストは計画の@WebMvcTestではなく、既存パターンに合わせてIntegrationTestBase（Testcontainers実DB）に統一した。本プロジェクトには@WebMvcTestスライスの前例が無く（Cart/Account等の既存Controllerテストは全て実DB統合テスト）、CSRF/JWT認証フィルタチェーンをスライスで再現する新規インフラ整備コストが見合わないと判断した。

② 在庫を実際に減算するテストは、既存カタログseed（EST-*）を使わず専用アイテム（ZZ-ORDER-*等）で隔離した。本Storyが本プロジェクトで初めてt_inventoryを書き換えるため、他specがEST-*の在庫数を前提にしているテスト（例: カートのAC-neg1テスト）を壊さないための方針。

③ InsufficientStockExceptionは在庫不足・空カートの両方の失敗を1クラスで表現した（itemId=nullが空カートを表す）。SM決定「空カートも在庫不足と同じ失敗系統（409）に寄せる」に沿った設計。

④ 配送先の解決（別配送を使うかどうか）はbackend側のPlaceOrderCommand#effectiveShipping()に集約した。useSeparateShipping=falseのときは請求先住所をそのまま配送先として複製する。フロントは常にbilling/shipping/フラグをそのまま送るだけでよく、判定ロジックを持たない設計にした。
