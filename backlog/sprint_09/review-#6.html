Sprint 09 Review

#6 — [E2] カート状態変更に CSRF 対策を施し REST 冪等性を整理する

Sprint 09 #6 security E2 / F2.3 backend
As a 買い物客　I want to カートの状態変更が正規のリクエストのみ受理されるようにしたい　So that CSRF による意図しないカート操作を防ぐ

なぜこの改修が必要だったか

Sprint 8（#4）／ #23 からの持ち越し課題

CSRF 基盤（cookie-to-header の非XOR方式・CsrfCookieFilter・非GETへのCSRFトークン必須化）と、カートの冪等メソッド割当（view=GET・add=POST・update=PUT・remove=DELETE）は既に実装済みだった。しかし (1) XSRF-TOKEN Cookie 自体には SameSite/Secure 属性が付いておらず JWT Cookie（access/refresh）と非対称だった、(2)「外部オリジンからの状態変更が拒否される」ことを検証する否定AC回帰テストが無かった、(3) 冪等性そのものを検証する回帰テストも無かった。

改修前（Sprint 8 / #23 時点）
CSRF有効・cookie-to-header非XOR・非GETにトークン必須（既達・変更なし）
冪等メソッド割当（GET/POST/PUT/DELETE）（既達・変更なし）
XSRF-TOKEN Cookie に SameSite/Secure 未設定（JWT Cookieと非対称）
外部オリジン拒否の否定AC回帰テストが無い
冪等性の明示回帰テストが無い
→
改修後
CSRF基盤・冪等メソッド割当（不変・既達を維持）
setCookieCustomizer で SameSite=Strict＋Secure を付与（JWT Cookieと統一）
外部オリジン拒否の否定AC回帰テストを新規追加
PUT/DELETE冪等性の回帰テストを新規追加

AC別 実装内容

✓
AC1 (SBD-3 / SBD-15)
add/update/remove の状態変更に CSRF トークン必須＋Origin/SameSite 検証。GET で状態変更しない

CSRF トークン必須自体は既達（変更なし）。今回追加したのは「XSRF-TOKEN Cookie 自体への SameSite=Strict＋Secure 付与」。計画フェーズ確定事項①により、新規の Origin/Referer 検証フィルタは追加せず、既存の cookie-to-header double-submit ＋ SameSite=Strict の組み合わせで Origin/SameSite 検証を充足する方針とした。

否定AC 回帰テスト — 攻撃が失敗することの実証

Phase 4（Verify）でそのまま再実行し「脆弱性が消滅していること」を確認する種となるテスト。攻撃者は被害者の XSRF-TOKEN Cookie を Same-Origin Policy により読み取れない、という前提を実際のリクエストで再現している。

🔒 AC-neg1（SBD-3） CSRFトークン偽造攻撃（Cookie値とヘッダ値の不一致） ✓ 攻撃失敗（403）
攻撃者は被害者ブラウザの本物の XSRF-TOKEN Cookie を読めないため、それらしく見える値をでっち上げてヘッダに載せるしかない。Cookie 値とヘッダ値が一致しない double-submit の照合失敗を再現。
POST /api/cart/items Cookie: XSRF-TOKEN=legit-looking-token-attacker-cannot-forge X-XSRF-TOKEN: attacker-cannot-know-this-value {"itemId":"EST-1","quantity":1}
↓ サーバの応答
403 Forbidden

↩ 設計確認 GET でのカート状態変更エンドポイントが存在しない ✓ 意図通り
CartController の状態変更3経路（追加/更新/削除）はいずれも @PostMapping/@PutMapping/@DeleteMapping のみで宣言され、GET で呼べる変更用エンドポイントは存在しない（罠 <img> タグ等によるGETベースCSRFの経路自体が無い）。
