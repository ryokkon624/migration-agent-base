Sprint 09 Review

#5 — [E2] カートの価格はサーバ権威・クライアントは数量のみ受理する

Sprint 09 #5 security E2 / F2.2 backend
As a サイト運営者　I want to 価格をサーバのマスター値で決定し、クライアントからは数量のみ受理したい　So that 価格改ざん（マスアサインメント）を防ぐ

なぜこの改修が必要だったか

Sprint 8（#4）からの持ち越し課題

カートAPIの価格は Sprint 8 の時点で既にサーバ権威（Item.listPrice からサーバ算出・リクエストDTOに価格フィールドなし）として実装済みだった。しかし (1) 「価格フィールドを送っても無視される」ことを検証する明示的な回帰テストが無く、(2) 数量の下限バリデーションが add / update / merge の3経路で統一されていなかった（add はSprint 8のセキュリティレビュー指摘で修正済みだが、update は int quantity のまま無検証、merge は quantity<=0 を黙って無視していた）。

改修前（Sprint 8 時点）
価格はサーバ算出・DTOに価格フィールドなし（既達・変更なし）
「価格注入が無視される」ことを検証する回帰テストが無い
update: int quantity・検証なし → 負数/非数値も無検証で通る
merge: quantity<=0 を continue で黙殺
→
改修後
価格はサーバ算出（不変・既達を維持）
価格注入無視のAC-neg1回帰テストを新規追加
update: @NotNull @Min(0) Integer → 欠落/負数400、0=削除は維持
merge: quantity<=0 → 400（黙殺廃止）

AC別 実装内容

✓
AC1 (SBD-2)
小計・単価はサーバが Item.listPrice（マスター価格）から算出。クライアントは価格/itemId 以外の権威値を送れない。受理するのは数量のみ

この挙動自体は Sprint 8 で実装済み（既達）。今回は挙動そのものを変えず、「価格フィールドを注入しても無視される」ことを明示的に検証する回帰テスト（AC-neg1）を新規追加し、Phase 4 verify でそのまま流用できる形にした。

否定AC 回帰テスト — 攻撃が失敗することの実証

Phase 4（Verify）でそのまま再実行し「脆弱性が消滅していること」を確認する種となるテスト。実際に悪意あるリクエストを組み立て、それが失敗する（無視される／拒否される）ことを assert している。

🔒 AC-neg1（SBD-2） 価格改ざん（マスアサインメント）攻撃 ✓ 攻撃失敗（無視される）
攻撃者が本来クライアントから送れないはずの listPrice（単価）・lineTotal（小計）・productName（商品名）を注入して、極端に安い価格でカートに追加を試みる。

🔒 AC2 不正な数量の直接送信（負数・欠落・非数値・merge黙殺値） ✓ 攻撃失敗（400で拒否）
UIの通常操作ではあり得ない値（負の数量・パラメータ欠落・文字列）を API に直接送りつけてカート内容の破壊やバリデーション回避を試みる。

動作確認ポイント（ユーザー確認用）

  • 1
    カート画面で通常の数量変更・削除がこれまで通り正しく動作すること 数量を0にすると行が消える挙動（既存動作）が変わっていないこと
  • 2
    商品をカートに追加・数量変更したときの単価・小計が、商品詳細ページに表示された価格と一致していること 常にサーバのマスター価格から計算されるため、画面操作だけでは価格はずれない
  • 3
    （開発者向け確認）ブラウザの開発者ツールでカートAPIのリクエストボディに価格を書き換えて送信しても、レスポンス・カート画面の表示価格はマスター価格のまま変わらないこと 上記「否定AC 回帰テスト」で自動化済み。手動でも同じ結果になることを一度確認すると安心

台帳（脆弱性差分台帳）への記載

今回は台帳追記なし。 update の「0=削除」セマンティクスは #4 の意図的仕様のまま維持しており、外部挙動の非等価変更は発生していない（計画フェーズ確定事項②）。緩い黙殺挙動を明示的な検証に置き換えたのは"堅牢化"であり、spec/台帳上の差分ではない。カート価格サーバ権威（SBD-2）・SQLインジェクション無し（SBD-17）は「維持項目」として、本スプリントの否定AC回帰テストが Phase 4 でそのまま"維持"の検証に使える。
