発見: domain.logic の branch 0% は「死んだコード」だった

🔍spikeの推論を実測が反証・実コードで確定した原因

spike時点の初期報告では「メールサーバ接続不能等でadvice冒頭からリターンしている可能性」と推測していた。 しかし legacy-jpetstore の実コード（applicationContext.xml）を確認した結果、原因は別（かつ確定的）だった。

legacy-jpetstore/src/main/webapp/WEB-INF/applicationContext.xml
<aop:config> <!-- <aop:advisor pointcut="execution(* *..PetStoreFacade.insertOrder(*..Order))" advice-ref="emailAdvice"/> --> </aop:config> <!-- AOP advice used to send confirmation email after order has been submitted --> <!-- <bean id="emailAdvice" class="org.springframework.samples.jpetstore.domain.logic.SendOrderConfirmationEmailAdvice"> <property name="mailSender" ref="mailSender"/> </bean>-->

SendOrderConfirmationEmailAdviceはbean定義・advisor設定の両方がコメントアウトされ、一度もインスタンス化されない。 シナリオを何本足しても分岐が動かなかったのは「未配線＝構造的に到達不能」だから。傍証: このクラスはInitializingBeanを実装し配線されていれば起動時に必ず1分岐は踏まれるはずだが、実測は0/6のまま = 「一度も生成されていない」という推論と完全に整合する。

結論: 「シナリオ不足」ではなく「死んだコード（未配線advice）を分母に数えていた見かけ上のギャップ」だった。 到達不能分岐は SendOrderConfirmationEmailAdvice（6）＋ MsSqlOrderDao（2・MS SQL Server向け代替実装で同様にコメントアウト）＝ 8分岐。 根拠は行番号つきで確認済み（applicationContext.xml L74-89・dataAccessContext-local.xml L68-73/L83-87、-jta版も同様の結論）。

除外を機構で担保する — report.sh の2本出し＋除外反証fail

「手計算の派生値はdriftする」への対応

実は合意プロセス中に一度、到達不能分岐の集計ミス（MsSqlOrderDaoのBRANCH 2を計算に反映し忘れ「到達可能分母36」と誤報告）が起きた。PO が jacoco.csv を直接パースして発見し、正しくは34と訂正した。 この経緯を踏まえ、除外の妥当性を脚注ではなくスクリプトが自動検証する仕組みに変更した。

  1. 1つの jacoco.exec から (a) AC1分母レポートと(b) ゲート分母レポートの2本を出力
  2. (a) の jacoco.csv から到達不能3クラスの行を取り出し、INSTRUCTION_COVERED/BRANCH_COVEREDが1でも0を超えたら即fail
  3. この検査を通過した場合のみ (b) ゲートレポートを生成
[report] verifying excluded classes remain unreachable (0 coverage) ... [report] OK: all excluded classes remain at 0 coverage (exclusion premise holds). [report] generating gate-denominator report (AC1 minus 3 unreachable classes) -> .../out2/report/gate [INFO] Analyzing 19 classes.

fail-path も実証済み: jacoco.csvのMsSqlOrderDao行を一時的に書き換えた合成データ（legacy実データは変更せず）でチェックロジック単体を実行し、期待どおり以下で終了コード1になることを確認した。

[report] FAIL: excluded class 'MsSqlOrderDao' now has coverage (instruction_covered=2, branch_covered=...). [report] '構造的に到達不能(未配線)'という除外の前提が崩れている。ゲート分母の再定義とPO再合意が必要（自動ラチェットはしない）。
