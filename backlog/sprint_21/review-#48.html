問題

「移植した業務ロジックが、本当に旧（Struts1 + HSQLDB）と同じ結果になるのか」を、これまで機械的に判定する手段がなかった。 現場で必ず問われる「①テストの本数は十分か ②網羅性は担保されているか」に、印象論ではなく実測と台帳で答えられる状態にする。

旧と新は語彙も分岐点も違う（旧＝Struts .do + HSQLDB、新＝REST + MySQL）ため、そのまま突き合わせることはできない。 どちらの語彙でもない正規形（canonical）を間に挟み、旧新それぞれの実測値を canonical へ写像してから比較する。

Struts1 .do 駆動
HSQLDB(9002) へ JDBC
JSP HTML から値抽出
"保存すべき業務ロジック"の正解
→
Canonical（正規形）
outcome / inventoryDelta
ordersCreated / orderTotal
lines（itemId, qty, unitPrice）

←

"同値であるべき"実装

旧新とも絶対値のシード（legacy EST-1=10000／new EST-1=100）が違うため、デルタ（増減）で比較する。 値が一致すれば EQUIVALENT、意図的に違うはずの箇所（ID-1・ID-29等）は INTENDED_DIVERGENCE(ID-x) を宣言し、宣言と実測が一致することまで判定する。

実装内容（AC別）

✓
AC1
canonical モデル — 旧新どちらの語彙でもない正規形
ParitySnapshot（outcome / inventoryDelta / ordersCreated / orderTotal / lines / entries）を新設。 新側 WHO 6列・version・自動採番ID・created_at/updated_at、旧側 creditcard/exprdate/cardtype/courier/locale/orderstatus/linenum は比較対象から除外。 金額は setScale(2) した文字列で保持し誤差0で比較する。
✓
AC2
デルタ比較 — シードの絶対値差を吸収する
在庫・注文件数は実行前後のデルタで比較する。orderid の値そのものは見ない（採番機構が違う＝ID-23）。旧 EST-1=10000・新 EST-1=100 というシード差があっても判定が成立することを確認済み。
✓
AC3
順序の正規化 — 並び順は比較対象にしない
集合性を持つ canonical は比較前に canonical キーで昇順ソート。ページング仕様自体を意図的に変えている（ID-20）以上、「保存すべき業務ロジック」に並び順は含めない、という判断。
✓
AC4
expectation の宣言と一致判定
ParityComparator が下記4分岐で判定する。
  • EQUIVALENT 宣言で差分が空 → pass
  • EQUIVALENT 宣言で差分あり → fail（台帳に無い差分＝欠陥候補）
  • INTENDED_DIVERGENCE(ID-x) 宣言で差分が空 → fail（台帳の形骸化）
  • INTENDED_DIVERGENCE(ID-x) 宣言で divergentFields 完全一致 → pass（宣言外の差分が混ざれば fail）
✓
AC5
シナリオ台帳 — 本Storyでは W1 の1本を登録
ParityScenarios を新設し、シナリオを抽象識別子で記述（例: USER_PRIMARY）。旧新それぞれの Runner が実体へ写像する。R1〜R6・W2・W3 は #49（横展開Story）のスコープ。
✓
AC6 / AC7
旧側 capture ハーネス — 別ポート・設定可能な接続先
captureGolden タスク（手動実行）が legacy を signon.do → addItemToCart.do → updateCartQuantities.do → checkout.do → newOrderForm.do → newOrder.do → newOrder.do?confirmed=true で駆動し、HSQLDB(9002) へ JDBC で読み出す。 legacy も新 backend も既定ポートが 8080 のため、採取用 legacy は別ポート（-p 8081:8080 -p 9002:9002）で起動し、base URL / JDBC 接続先は -P オプションで差し替え可能（ハードコードしない）。
✓
AC8
golden の版管理 — 再現性の担保
src/test/resources/parity/golden/*.json にコミット。capturedFrom.legacyCommit（legacy repo の commit sha）と capturedAt を必ず埋める。sha を解決できなければ書き出さずに fail。
✓
AC9 / AC10
新側 verify の駆動 — 実HTTP・CSRFヘルパ・シナリオ間リセット
@SpringBootTest(webEnvironment = RANDOM_PORT) の実HTTPで新側を駆動（MockMvcの csrf() 注入は使わない＝フィルタチェーン実経路を通すため）。DBは既存 IntegrationTestBase の Testcontainers MySQL 8.4 + Flyway を再利用。 各シナリオ実行前にカート／注文／在庫を既知状態へリセットする前処理を実装（前シナリオのカート残留による誤カウントを防止）。
✓
AC11 / AC12
dual-tag と gradle タスク — legacy 停止状態でも green
Spec は @Tag("integration")＋@Tag("parity") の dual-tag。parityTest（includeTags 'parity'）を新設し、既存 integrationTest に excludeTags 'parity' を追加して二重実行を回避。check には載せない（当面ローカル/手動ゲート）。 legacy を停止した状態でも parityTest がコミット済み golden とのみ比較して green になる（legacy 起動が要るのは captureGolden のみ）。
✓
AC-neg2
legacy 無改変 — 採取後の後始末
採取のために legacy のソース・WAR・run/ 配下は一切変更しない。DBデータ操作は可とするが、採取後は復元する（下記「実装メモ」参照）。

AC-neg1 実証 — 台帳に無い不一致は失敗する

golden order-single-item.json の unitPrice を "16.50" → "16.99" へ一時的に書き換え、parityTest を実行した実際の失敗出力。

$ ./gradlew parityTest --tests "*OrderParitySpec"   Condition not satisfied:   result.pass | | | false scenario=order-single-item: EQUIVALENT宣言だが差分あり(台帳に無い差分=欠陥候補) -> field=lines[EST-1].unitPrice golden(legacy)="16.99" actual(new)="16.50"   BUILD FAILED
どのシナリオのどのフィールドが食い違ったかが出力から一目で判別できる。goldenを "16.50" へ戻すと再び green になることも確認済み。

実装メモ（仕様外の判断・変更・妥協点）

CSRFヘルパの罠（spikeで4回踏んだ落とし穴の実機再現）

NewHttpClient.ensureCsrfToken() の初版は Groovy の (1..N).each { ... return token } でリトライしていたが、Groovyのクロージャ内 return は .each{} を抜けず continue 相当にしかならないため、トークンが早期に取れてもループが最後まで回り成否が不安定になる不具合だった。OrderParitySpec 実行時に以下の試行履歴つき例外で実際に検出できた:

XSRF-TOKEN Cookieが10回のGET /api/pingでも取得できなかった: attempt 1: present, attempt 2: absent, attempt 3: present, attempt 4: absent, attempt 5: present, attempt 6: absent, attempt 7: present, attempt 8: absent, attempt 9: present, attempt 10: absent

この出力自体が「トークンCookieの有無が交互にトグルする」という新側CSRFの仕様の実機再現になっている。素の for ループ（トークン取得次第でメソッド自体を return）へ書き換えて解消した。
