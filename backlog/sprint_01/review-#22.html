Sprint 01 Review

#22 — DB移行基盤（Flyway・MySQL 8.4）を整備し
スキーマを移行する

Sprint 01 #22 foundation jpetstore-database

なぜこの改修が必要だったか

問題

legacy（HSQLDB + iBATIS）のスキーマは、①ログイン/アカウント取得が bannerdata との INNER JOIN に依存し該当行が無いと失敗する、②パスワードが平文格納可能な varchar(25)、③カード情報・courier・locale を無意味に永続化、④金額計算の丸め誤差対策が不十分、⑤認可失敗・状態変更を記録する監査ログが存在しない、⑥後勝ち更新を防ぐ楽観ロックが無い、という secure-by-default 上の欠陥を抱えていた。全ドメイン実装の前提となる最上流のため、Sprint 1 で MySQL 8.4 + Flyway 基盤ごと作り直す。

改修前（legacy）
HSQLDB 1.8 + iBATIS 2
ログイン取得が bannerdata と INNER JOIN（該当行が無いと失敗）
signon.password varchar(25)（平文保存前提）
creditcard/exprdate/cardtype・courier・locale を永続化
orderId は sequence テーブルの非アトミック採番
orderstatus は1行だけの異形テーブル（linenum=orderId）
監査ログ無し・楽観ロック無し
→
改修後（V00_000_003〜006）
MySQL 8.4 + Flyway（DB名 jpetstore_db）
bannerdata 自体を持たない＝JOIN依存が構造的に消滅
m_signon.password_hash varchar(255)（ハッシュ格納前提）
カード列/courier/locale を一切持たない
t_order.order_id は AUTO_INCREMENT（原子採番）
orderstatus 廃止 → status_code(placeholder) + audit_log
t_audit_log 新設・m_account/m_signon/m_profile に version 楽観ロック

スキーマ設計の要点（WHO列・version付与範囲）

全12テーブルの種別・WHO6列・version楽観ロックの付与状況。version は m_account / m_signon / m_profile の3表のみ（architecture-conventions §4.2/§4.3 準拠）。

意図的除外（legacyから持ち込まないもの）

🚫 bannerdata テーブル / banneropt・mylistopt 列
AC3・ID-7。ログイン/account取得のINNER JOIN依存を構造的に解消。
🚫 creditcard / exprdate / cardtype 列
AC5・F3.6・ID-8。実カードを永続化しない（支払は非実装のプレースホルダ）。
🚫 courier / locale 列
ID-21。プレースホルダ機能のためスコープ簡素化。
🚫 orderstatus / sequence テーブル
ID-22・ID-23。status_code+audit_logへ統合／AUTO_INCREMENTの原子採番に置換。

実装メモ（仕様外の判断・変更・妥協点）

列名を legacy の省略形からフルワードへ拡張。 descn→description、addr1/2→address1/2、zip→postal_code、suppid/catid/productid/itemid→supplier_id/category_id/product_id/item_id 等。ACのAC2/AC4対象列（password_hash/total_price/unit_price等）が既にフルワード表記だったため、命名の一貫性を優先し全カラムに適用した（構造スキーマ差分のため intended-diff-ledger の対象外）。

t_audit_log.actor_user_id にFK制約を付けない。 存在しないusernameへのログイン失敗対応と、アカウント削除後も監査証跡を保持する必要性の2点から。

flyway/sql-test のバージョン採番を V01_000_001 から開始。 sql-test側の採番規約が未整備だったため、flyway/sql（00_xxx_xxx）と衝突しない別レンジを新設した。

【既存build.gradleのバグを発見・修正】 seedDevDataタスクのlocationsがflyway/sql-testのみを指しており、flyway/sql側マイグレーションが実在するとFlywayのvalidateが Detected applied migration not resolved locally で失敗し、README記載のflywayClean→flywayMigrate→seedDevDataフローが壊れる状態だった。AC-neg1テスト実装中に発覚し、locationsに両方を含めるよう修正。ローカルDocker MySQLで実際に復旧を確認済み。

【レビュー対応】m_item.supplier_id に明示セカンダリインデックスを追加。 performance-reviewer指摘。兄弟のproduct_idは明示KEY idx_m_item_product_idを持つのに、supplier_idはFK索引の自動生成任せで非対称だったため、基盤スキーマの一貫性・自己文書化のため揃えた。
