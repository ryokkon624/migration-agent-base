### Sprint 1（2026-08-13）— E6基盤系（#22 DB移行）計画フェーズより

DEVからSprint1計画フェーズでユーザーに直接確認した事項をSM経由で中継され、5件を質問ログに記録した（全て初出のトピックのため、本Retroでは個別のチェックリスト昇格は見送り、傾向記録に留める）。

- 命名規約（m_/t_プレフィックス等）が spec に明文化されていない
- 代理キー（surrogate key BIGINT）導入の是非・WHO前提との整合
- orderstatus表廃止＋status_code列への統合という具体的な統合方式
- Sprint1のseed範囲（DDLのみかバルクseed含むか）
- （参考・バックログ修正不要と判定）DB専用リポジトリでのTDD検証手段＝Testcontainers採用の是非。実装手段の選択はDEV裁量の領域に該当。

**傾向**: Acceptance Criteria は DDL の"何を"（テーブル・列・制約）は書くが、命名規約・PK戦略・既存表の統合/廃止方式・seed範囲といった"どう作るか/どこまでやるか"の基盤決定が未定義になりがちで、実装直前の確認に集中した。5件中4件はAC/備考への先回り明記で防げた可能性があった。

**所感（次回Refinementでの適用方針）**: E6基盤系Story（DB移行・backend/frontend土台など新規リポジトリ着手のStory）を起票・詳細化する際は、Refinement段階で以下の観点をAC/備考に先回り明記できないか確認する。ただし本トレンドは今スプリントが初出のため、正式なチェックリスト項目への昇格は次回以降に同種の質問が出た場合に判断する。

- テーブル・列の命名規約（プレフィックス・大小文字規則）
- 主キー戦略（surrogate/natural key、型。WHO列などの前提整合）
- 既存テーブルの統合・廃止方針（対象列名まで具体化して明記）
- Sprint内のseed/fixtureスコープ（DDLのみか、バルクデータ投入まで含むか）
