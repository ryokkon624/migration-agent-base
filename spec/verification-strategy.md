# verification-strategy — Phase 4 検証戦略（旧新の"正しさ"をどう担保するか）

> **目的**: 「旧システムを正しく再現できたか」をどう証明するかを定める。
> **立場**: AI Factory は **1:1 再現ではなく仕様源からの作り直し**。よって"旧と完全一致"を品質基準に置けない/置くべきでない部分がある。本書は **① AC準拠（一次）＋② 特性化テストで"保存すべきロジック"の旧同値を採る（現場流）＋③ セキュリティ回帰＋④ 意図差分は台帳で宣言** のハイブリッドを定義する。
> **背景**: Velocity White Papers には旧新パリティ/回帰/並行稼働の方法論は**無い**（正しさは ground-truth(コード)→spec(AC)→4レビューエージェント→human verify で担保）。本書はその穴を現場知見で補う。→ [`architecture-conventions.md`](./architecture-conventions.md)・[`security-baseline.md`](./security-baseline.md)・[`backlog-map.md`](./backlog-map.md)

## 0. なぜハイブリッドか（3つの前提）

- **旧＝"理解の源(ground truth)"であって、テストの正解(oracle)ではない**。
- ただし業務ロジックの一部は「**意味的に保存**」が要件（例: 在庫減算の結果、注文合計、税計算）。ここは旧を実測して同値を採る＝**特性化テスト**。
- **変える所**（セキュリティ是正・`BigDecimal`化・UI刷新・機能廃止）は「**差分＝仕様**」。**意図差分台帳**で宣言し、「差分＝バグ」の誤解を断つ。
- **生DBダンプの行一致は狙わない**（スキーマが違う：WHO列/version/採番/HSQLDB→MySQL）。比較は**業務カラムの意味レベル**で行う。

## 1. 4つの検証レイヤ

| レイヤ | 何を検証 | 正解の源 | 主担当 | フェーズ |
| --- | --- | --- | --- | --- |
| **L1 AC準拠テスト** | 各 Story の AC を満たすか | 抽出仕様（`behavior/*`・`backlog-map`） | DEV | Phase 3（実装と同時） |
| **L2 特性化テスト（旧同値）** | 保存すべき業務ロジックの「入力→出力＋DB意味デルタ」 | legacy 実測（golden fixtures） | DEV | Phase 3 |
| **L3 セキュリティ回帰** | before の PoC が after で**失敗**すること | `reports/before` の finding/PoC | SEC / security-* | Phase 4 |
| **L4 意図差分の確認** | 変えた振る舞いが**台帳どおり**か | 意図差分台帳（§4） | PO / SM | Phase 4 |

## 2. Golden fixture の採取（凍結アーティファクトなので"いつでも"でよい）

- **legacy は改変・破棄しない前提の凍結アーティファクト**（公開リポジトリ＋Docker で常に再現起動可能）。よって採取は**時間に敏感でなく、L2 実装時（Phase 3）に必要な分だけ**行えばよい（事前の専用ステップは不要）。
- 「いつでも同値が採れる」ための前提2つ：
  - **再現起動のピン留め**：Docker イメージ/タグと HSQLDB seed を固定。`now()`・採番など非決定な出力は §3 の正規化で吸収する。
  - **採取物の版管理**：採った fixtures は `reports/before/golden/` に**コミット**し、**採取時の legacy コミットハッシュ**をメタに残す（CI 再現・監査可能に。ローカル一発芸にしない）。
- 採取シナリオ＝`behavior/*` のドメインに対応：カタログ閲覧 / カート / **注文（在庫減算含む）** / アカウント / 認証。
- **注意**：legacy は意図的に脆弱＝一部は"再現しないのが正しい"（平文PW・IDOR 等）。採取はするが **L2 の期待値には使わず L4（差分台帳）へ回す**。

## 3. 特性化テスト（L2）の比較ルール

- **正規化（比較から除外）**：WHO 6列 / `version` / `created_at`・`updated_at` / 自動採番ID / セッション依存値。
- **比較に含める**：金額・数量・**在庫増減**・ステータス遷移・関連レコードの有無/件数。
- DB比較は「**操作前後のデルタを意味単位で**」（例：item X を2個注文 → `available_qty` が 2 減 / `t_order` 1件 / 明細合計＝単価×数量）。
- 金額は `BigDecimal` 化で丸めが変わり得る → **意図差分なら台帳（ID-3）**、そうでなければ許容誤差 0。

## 4. 意図差分台帳（intended-diff ledger）

「旧と違ってよい／違うべき」を明示。**PO 所有・レビュー承認**。`reports/before` の findings からほぼ機械的に起こせる。

| # | 旧の振る舞い | 新の振る舞い | 理由 | 由来 |
| --- | --- | --- | --- | --- |
| **ID-1** | 在庫ガード無し減算（売り越し可） | `qty>=n` ガード＋在庫不足で注文失敗 | 売り越し防止 | D6 / SBD-2 |
| **ID-2** | パスワード平文保存 | ハッシュ＋ソルト | 資格情報保護 | SBD-5 |
| **ID-3** | 金額 `double` | `BigDecimal` | 丸め正確性 | SBD-13 |
| **ID-4** | 連番 orderId で他人注文参照可（IDOR） | 認可＋識別子不透明化/応答統一 | アクセス制御 | SBD-1 / SBD-8 |
| **ID-5** | Hessian/Burlap/Axis 等 remoting 面 | 廃止（REST・認証必須） | 攻撃面除去 | SBD-7 |
| **ID-6** | JSP / サーバレンダリング | SPA＋REST | モダン化 | D1 |
| **ID-7** | banner / MyList | 廃止 | スコープ決定 | backlog-map |

> 台帳は生きた文書。Story 起票時に「振る舞いを変える」と判断したら**必ず追記**する。**台帳に無い差分＝要調査（＝欠陥候補）**。

## 5. Phase 4 の合否ゲート（migration の Definition of Done）

- **L1**：全 AC テストが green。
- **L2**：保存ロジックの特性化テストが旧同値（台帳の意図差分を除く）。
- **L3**：before の PoC が **すべて after で失敗**（脆弱性消滅の実証）。
- **L4**：実測された差分が**すべて台帳に載っている**（未台帳の差分＝要調査）。
- **出力**：`reports/after/verification-report.md`（＝ステークホルダー提出物）。

## 6. 使いどころ（誰が・いつ・何のために）

| タイミング | 使う人 | 使い方 |
| --- | --- | --- |
| **Refinement（PO稼働中＝今）** | PO | AC に「**L2 特性化の種**」フラグを付ける／振る舞いを変える判断は**意図差分台帳へ**。 |
| **Phase 3（実装, L2時）** | DEV | L1（AC）と L2（特性化）テストを実装。**L2 の際に legacy を起動して golden fixture を採取→コミット**（§2。凍結アーティファクトなので事前ステップ不要）。 |
| **Phase 4（検証）** | SEC | L3（セキュリティ回帰＝before PoC が消えたこと）。 |
| **Phase 4（検証）** | SM/PO | L4＋§5 合否ゲート判定＋`verification-report` 作成。 |
| **Review / Retro / 記事③** | 全員 | 「正しく再現した」の**証拠＝台帳＋パリティレポート**。日本的な「(中身は知らないが)何も変わっていないと証明しろ」への**直接の回答**になる。 |

> 使いどころの本質：この文書は **PO の AC を"検証可能"にする補助線** であり、**Phase 4 の品質ゲート** であり、**ステークホルダー説明の武器**。特に **意図差分台帳** が、AI Factory（非1:1再現）と「変わってもらっては困る」要求の**衝突を解く鍵**になる。
